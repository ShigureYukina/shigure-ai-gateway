# 故障注入下的网关表现

> **状态：数据已采集（2026-10-13，Docker 环境，有 Redis）。**
> 与 `README.md` 基线的剩余差异只有一处：CPU 被 `.wslconfig` 限到 4 核（基线是 12 核），
> 见第二节。本文件的绝对吞吐低于基线是已知原因，不是新问题；
> 三组场景之间的相对结论不受影响。

## 一、为什么必须单独测

`README.md`（性能基线）那套数字是在**全链路健康**的上游下测的。那份文档第八节写明它的边界：

- 缓存、限流、安全过滤、熔断 fallback 均为关闭状态，这些路径的延迟没有覆盖；
- **未做故障注入（上游 500 / 超时 / 慢响应）下的网关表现。**

也就是说：网关里最贵的那部分代码——错误归类、熔断计数、跨供应商回退、首字节硬边界、
配额退还、探测的假失败防护——在健康上游下**一行都跑不到**。代码有单测证明逻辑正确，
但没有端到端数据说明它在真实时序下表现得怎么样。

## 二、与基线的已知差异

| 项 | `README.md` 基线 | 本次采集 |
| --- | --- | --- |
| 网关 / 上游 / Redis | Docker 容器 | Docker 容器（一致） |
| **CPU** | **12 核（未做限额）** | **4 核（`.wslconfig` 限的）** |

CPU 是唯一的差异，而且是**环境限制**而非配置失误：本机试过把 `.wslconfig` 的
`processors` 提到 12（正好等于宿主逻辑处理器数），HCS 直接建不出虚拟机
（`Wsl/Service/CreateInstance/CreateVm/HCS/ERROR_NO_SYSTEM_RESOURCES`），退回 4 才能启动。

代价是吞吐：同样 200 请求 / 并发 20，本机 baseline 390.75 RPS，
而基线是 503.19 RPS。**延迟口径受影响小得多**（P50 45.26ms vs 37.7ms），
因为上游固定 35ms 是延迟的主体，CPU 数主要压在并发处理上。

要消除这个差异需要一台能开出 12 核 VM 的机器。在那之前，
本文件的绝对吞吐不要与 `README.md` 并列引用。

> 补一条历史：第一版采集是在**本机进程 + 完全没有 Redis** 的条件下做的，
> baseline P50 47.21ms / 360.58 RPS。改成 Docker（有 Redis）后是 45.26ms / 390.75 RPS。
> 也就是说无 Redis 只值约 2ms —— 当时把它当成主要偏差是判断偏了，
> 主要偏差其实是 CPU。

## 三、口径

- 用**同一个** `scripts/load_test.py` 算百分位（`--only non_stream_success`），
  不另写统计代码——否则基线与故障场景的分位数不可比。
- 每组都是**全新的网关进程**，熔断器状态不跨组继承。
- **预热对着健康上游做**：先用健康 mock 跑 200 请求 / 并发 8 把 JVM 带热，再切成故障 mock。
- 注入比例用 `--seed 42` 固定。
- 对照组在同一次会话里重跑，不复用 `README.md` 的基线数字。

### 3.1 采集过程中修掉的两个方法错误

留在这里是因为它们和结论一样重要——**第一个错误直接产出了完全错误的数字**。

**错误一：熔断器状态跨组继承。** 第一版脚本只在对照组和超时组重启网关，
于是 429 那组继承了 500 组累积的熔断器状态，整轮都跑在「已熔断」状态下，
测出来的是熔断后的快速失败。表现是 429 组成功率 10%、P50 40.87ms——
看起来像「429 一上来就全挂」，其实大部分请求根本没走到上游。
修正：每组前都重启网关。

**错误二：预热对着故障上游做。** 第二版加了重启，但仍沿用「先注入再预热」。
熔断参数是 `sliding-window-size=20` / `minimum-number-of-calls=10` / `failure-rate-threshold=50%`，
40 个故障请求**必然**触发跳闸。于是超时组整轮都测在已熔断状态：
成功率 0%、**Max 延迟只有 66.31ms**——一个配了 2s 超时的场景，最大延迟 66ms，
这个数字自己就说明测量是错的。
修正：预热用健康上游，故障只在正式测量阶段注入。

两个错误有同一个共同点：**都是「测量对象已经被上一阶段改变了」**。
故障注入场景和健康压测的根本差别就在这里——健康压测里前一段的状态不会影响后一段。

## 四、结果

200 请求 / 并发 20，上游固定 35ms。延迟单位 ms。

| 场景 | 成功率 | 吞吐 RPS | P50 | P95 | P99 | Max | 状态码分布 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| baseline（健康） | 100% | 390.75 | 45.26 | 65.86 | 74.25 | 93.99 | 200 × 200 |
| error500（10% 500） | 99% | 360.12 | 48.94 | 82.14 | 99.32 | 106.14 | 200 × 198，504 × 2 |
| ratelimit429（25% 429） | 8% | 557.61 | 30.86 | 66.05 | 101.38 | 108.10 | 200 × 16，500 × 181，504 × 3 |
| hang-timeout（上游不回包，超时 2s） | 0% | 49.38 | 25.05 | 2045.12 | 2067.78 | 2074.17 | 500 × 200 |

原始数据：`fault-baseline.json` / `fault-error500.json` / `fault-ratelimit429.json` /
`fault-hang-timeout.json`（每组另有一份 `-warmup.json`，仅用于预热，结果丢弃）。
本表只是摘要，不引入 JSON 之外的二次计算。

### 4.1 一个必须先说的读数陷阱

**429 组和超时组的吞吐有升有降，但成功率是 8% 和 0%。**

429 组吞吐 557.61 高过 baseline 的 390.75，原因是熔断器跳闸之后失败返回得快：
请求在 ~31ms 就被拒，不用再等上游的 35ms。**失败得越快，吞吐数字越好看。**

而超时组吞吐只有 49.38（远低于 baseline）——它不是「快速失败」，是真的每个请求都等满了超时。

两个方向相反的读数说明同一件事：**任何一组都必须把成功率一起看**。
这也是第三节那两个方法错误能蒙混过关的原因——它们的数字都「看起来很合理」。

### 4.2 每组的判据与结论

**error500：重试吸收了瞬时 5xx。**
200 个请求注入 10% 的 500，客户端只看到 2 个失败（504「上游重试耗尽」），
成功率 99%，P50 48.94ms 与 baseline 45.26ms 相差 3.7ms（约 8%）。
上游 500 的响应体被包进 504 的 message 里，没有原样透出——`UpstreamCallExecutor` 的
错误体截断生效。熔断器全程未跳闸（10% 失败率低于 50% 阈值，符合配置）。
**代价**：吞吐和延迟几乎看不出 10% 的请求多打了一轮，只有成功率掉了 1 个点。

**ratelimit429：熔断器在头 19 个请求内就跳闸了。**
分布是 16 个成功 + 3 个 504（429 重试耗尽）+ 181 个 500「CircuitBreaker is OPEN」。
181 = 200 − 19，也就是说熔断发生在第 19 个请求附近。
按 `minimum-number-of-calls=10` / `failure-rate-threshold=50%`，25% 的 429 连续出现时，
十个请求里五个失败就够跳闸——**熔断器的反应比预想的快得多**。
这带来一个值得注意的后果：一次性 25% 的限流足以让整个渠道被摘掉，
即使剩下 75% 的请求本可以正常成功。这是不是想要的策略，取决于业务能否接受
「宁可全挂也不 partial 成功」；至少在面试里要知道这个行为存在。

顺带确认了 429 在两条路径上的处理是**不同**的：转发链路把它记为通道故障
（会推高熔断失败率），而后台健康探测明确**不**把它计入失败计数
（`ChannelProbeService` + `ChannelProbeServiceTest.shouldNotCountRateLimitAsFailure`）。
前者保护单次请求，后者保护渠道不被误摘——本组数据里跳闸的是前者，与代码注释一致。

**hang-timeout：超时生效在配置值附近，但代价是熔断前有一批请求各阻塞满 2s。**
P95 2045.12ms / Max 2074.17ms，对配置的 2000ms 超时多出约 45–74ms——超时没有
「远大于配置值」的失控。P50 只有 25.05ms，两者是双峰分布：第一波约 20 个并发请求
各自阻塞满 2s（这批把熔断器顶开了，≥`minimum-number-of-calls=10` 且全部失败），
之后其余请求在 ~25ms 被熔断器直接拒掉。吞吐跌到 49.38 RPS 也印证了这一点：
这一组是真的等满了，不是快速失败。
**所以超时确实会计入熔断失败**——这一点值得记下来，因为它反直觉：
`.timeout()` 在算子链最外层（`UpstreamCallExecutor.java:204-206` 的顺序是
`timeout` → `retryWhen` → `circuitBreaker` → 调用），直觉上最外层的超时取消内层时，
熔断器可能只收到 cancel 而收不到 error、于是不记失败。
实测不是这样：熔断器在超时场景确实跳闸了。
（本条的机制解释没有进一步做实验验证，这里只记实测行为，不下因果结论。）

另外可见：熔断器拒绝时不走重试——181 个 `CallNotPermittedException` 在 ~31ms 内返回，
没有出现重试风暴。原因是 `.retryWhen` 在熔断器外层，但其重试谓词按状态码过滤，
`CallNotPermittedException` 不在其中。

### 4.3 一个附带验证：Redis 完全缺席时的 fail-open

这个结论来自第一版采集（无 Redis 的那轮），保留下来因为它是一次意外的对照实验：

- baseline 组 200 个请求 **全部 200**，成功率 100%
- 同期日志里有 2,006 行 `Connection refused`、21,020 行 Redis 相关记录
- 也就是说：**每一次指标写入都失败了，而没有一个请求因此失败**

这正是 `AiGatewayMetricsRecorder` 的设计意图（fire-and-forget、写失败只 `log.warn`），
现在有端到端数据了，不只是代码注释。被问到「Redis 挂了会怎样」时可以答：
指标与账本类写入全部 fail-open，请求照常返回——本次故障注入里顺带测到了。

**但有一条不能顺带认领**：`rate-limit.enabled` 默认 false，
所以**配额预扣/退还的 fail-open 两轮都没有走到**。`ProviderRateLimitService` 的 fail-open
目前只有单测（`onErrorResume` → `Mono.just(true)`），没有端到端数据。

### 4.4 三组都没覆盖的

- **跨供应商回退仍然没测到。** harness 只配了一个 provider
  （`provider-base-url.openai`），回退链需要两个以上可用通道，而通道走管理 API 建。
  所以 `fallback-enabled` 默认关闭这件事在这三组里没有变化，
  「首字节硬边界」也只有单测没有端到端数据。**面试时要主动说这一点。**
- 首包 / 流式场景未注入（本次只跑 `non_stream_success`）。流式的首字节硬边界
  与流式配额结算在故障下如何表现，完全未知。
- 没有「故障恢复」维度：`wait-duration-in-open-state=10s` 之后熔断器半开、探测恢复的过程
  没有观测到。要看这个需要在同一组内延长压测时长。
- 没有长时间稳定性观察，单轮 0.24~2.28s。

## 五、复现

```bash
export MSYS_NO_PATHCONV=1
cd E:/DeepSeek-work/shigure-ai-gateway
bash scripts/run_fault_injection.sh
```

脚本自己会 `export MSYS_NO_PATHCONV=1` 并用 `cygpath -m` 取仓库路径，
不需要调用方预先处理——否则 `-v "$CTX/...:/app/app.jar"` 里的 `/app/app.jar`
会被 MSYS 转成 `C:/Program Files/Git/app/app.jar`，报 "Unable to access jarfile"。

第一版采集是在「本机进程 + 完全无 Redis」的条件下做的，用来验证方法本身可用；
上表的数据来自 Docker 版的完整一轮。两轮的**场景间相对结论一致**，
差别只在绝对值（见第二节末的补充）。

脚本与 mock 的注入参数：

| 参数 | 作用 |
| --- | --- |
| `--error-rate` | 比例返回 500 |
| `--rate-limit-rate` | 比例返回 429 + `Retry-After: 1` |
| `--hang-ms` | 收到请求后额外延迟，且不主动断开连接 |

429 与 500 在注入顺序上**先判 429**、两者独立取样，
所以 `--error-rate 0.5 --rate-limit-rate 0.25` 得到的是 25% 的 429、
其余中的 50% 为 500，而不是互相覆盖。
